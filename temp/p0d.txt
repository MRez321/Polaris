# P0-D — Sales & Channels (17–25)

## Mission

Implement P0-D for Polaris as a unified sales architecture covering:

17. Seller
18. Sales Channel
19. Wholesale Sales
20. Consignment Sales
21. Seller Sales
22. Customer
23. Unified Order
24. Order Lifecycle / Status
25. Payment & Settlement

Do not redesign unrelated modules. Do not delete the existing website checkout/order system prematurely. Preserve backward compatibility and integrate the new model safely.

The target architecture is:

Channel → Unified Sales Order → Customer / Seller → Order Lines → Payment → Inventory Movement / Settlement

For consignment:

Warehouse → Consignment Handover → Seller Inventory → Seller Sale → Commission → Settlement / Return

# STEP 6 — Seller Sales Service

Implement:

```text
createSellerSale()
listSellerSales()
getSellerSale()
```

Validation:

* seller exists
* seller is active
* channel exists and is active
* lines are non-empty
* quantity is positive integer
* price is non-negative
* commission rate is between 0 and 100
* item exists and is not deleted

Calculation:

```text
subtotal = Σ(quantity × unitPrice)

commission =
    percentage commission:
        subtotal × commissionRate / 100

netSettlement =
    subtotal - commission

settledAmount = 0

remainingSettlement =
    netSettlement
```

Use database transactions.

Create:

`backend/src/modules/workshop/salesService.ts`

```text
createSalesOrder()

```

```text

customerAddress?

taxAmount?
sourceReference?
utmSource?

```

For every line:

1. Verify item exists.
2. Read item data from database.
3. Determine unit price server-side unless an explicitly permitted sales price is supplied.
4. Validate quantity.
5. Validate discount.
6. Calculate line total.
7. Snapshot item identity.
8. Calculate order subtotal.

Then:

```text
total =
    subtotal
    - discount
    + shipping
    + tax
```

Initial state:

```text
status = draft
paymentStatus = pending
paidAmount = 0
remainingAmount = total
```

Use a database transaction.

# STEP 11 — Customer Order Payment

For an Order:

```text
newPaidAmount =
    currentPaidAmount + paymentAmount

remaining =
    totalAmount - newPaidAmount
```

Reject overpayment unless the existing financial architecture explicitly supports overpayment.

Set:

```text
remainingAmount
paymentStatus
paidAt
```

When fully paid:

```text
paymentStatus = paid
```

If partially paid:

```text
paymentStatus = partial
```

All updates and payment insertion must happen inside one database transaction.

---

# STEP 12 — Seller Settlement

For Seller Sale:

```text
newSettledAmount =
    currentSettledAmount + paymentAmount

remainingSettlement =
    netSettlementAmount - newSettledAmount
```

Reject settlement above the outstanding amount.

When zero:

```text
status = settled
```

Otherwise preserve the current valid seller-sale status.

Do not fake settlement by simply changing a status. Store every actual payment/settlement transaction.

# STEP 18 — Consignment Integration

Do not replace existing consignment.

Keep:

```text
Consignment
ConsignmentItemLine
Handover
Return
Seller Inventory
```

Add the missing distinction:

```text
handover ≠ sale
```

A handover means inventory moved into seller custody.

A seller sale means seller actually sold the item.

A return means unsold/returned inventory comes back.

A settlement means money owed to/from seller is financially settled.

These events must not be collapsed into one record.

# STEP 24 — Validation

Before considering P0-D complete, test at minimum:

### Channels

* duplicate channel code rejected
* inactive channel rejected

### Customer

* customer can be attached to order
* customer can exist without website User
* customer purchase totals remain consistent

### Order

* empty order rejected
* invalid item rejected
* zero/negative quantity rejected
* invalid price rejected
* excessive discount rejected
* total calculated server-side
* remaining amount calculated server-side

### Status

* invalid transition rejected
* valid transition accepted
* cancelled order cannot receive payment

### Seller

* inactive seller rejected
* invalid commission rejected
* seller sale subtotal calculated server-side
* commission calculated server-side
* settlement cannot exceed outstanding amount

### Payment

* zero payment rejected
* negative payment rejected
* payment without target rejected
* payment with two targets rejected
* overpayment rejected
* partial payment produces `partial`
* full payment produces `paid`
* full seller settlement produces `settled`

### Inventory

* sales code does not directly mutate stock
* inventory changes use existing inventory/ledger mechanism

### Audit

* sales creation audited
* payment audited
* settlement audited
* status transition audited
