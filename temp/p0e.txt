P0-E — MANAGEMENT EXPERIENCE
Scope: items 29–35, 39, 40

MISSION
Improve Polaris management UX so the application behaves like an operations/management system:
- clear operational navigation
- action-oriented dashboard
- consistent forms/tables/states
- responsive desktop/mobile experience
- global search
- activity/audit timeline

DO NOT:
- change backend/domain architecture
- invent entities that do not exist
- create fake suppliers/customers/orders/data
- break existing routes or APIs
- replace working P0-B/C/D functionality
- rewrite the existing dashboard unnecessarily
- remove existing MobileNav
- introduce a second design system

==================================================

- responsive overflow

==================================================
ACCEPTANCE CRITERIA
==================================================

P0-E is complete only when:

[29] Navigation clearly represents Polaris operations rather than production/workshop-first IA.

[30] Dashboard answers:
     "What needs my attention now?"

[31] Shared FormField/DataTable primitives exist and follow Polaris conventions.

[32] Desktop/tablet/mobile layouts work without overflow.

[33] Forms have consistent labels, validation, loading, success and error behavior.

[34] Management tables support appropriate search/filter/sort/responsive/empty/loading states.

[35] Errors are actionable and never silently disappear.

[39] Global search works against real available entities and supports Ctrl/Cmd+K.

[40] Dashboard exposes recent real Audit activity through a reusable timeline.

FINAL RULE:
Prefer the smallest safe change that achieves the requirement.
Reuse existing Polaris components, APIs, types, styles and architecture.
If a requirement depends on an entity/API that does not yet exist, DO NOT fake it—leave that integration for the relevant P0-B/C/D implementation.
